# P08. 组件库拆分：基础库 + 独立复杂组件库（含一键 antd 化扩展与命名别名）

- 状态：`[ ]`
- 目标：将 antd_flutter_plus 全量包拆分为「基础组件库（antd_flutter_ui）+ 独立复杂组件库」，支持全量接入与单独接入；同步实现 `Text('123').antd` 一键扩展语法与 Flutter→antd 命名别名层；拆分必须有足够理由，不为拆而拆
- 前置依赖：建议在 P03/P05/P07（antd_theme 增强）之后执行，避免拆分期间主题层接口变动；纯规划阶段可提前

## 拆分原则（核心）

### 独立拆分准入标准（同时满足越多越应拆，硬性至少 3 条）
1. **功能复杂度**：组件实现复杂（自绘引擎/复杂手势/状态机），代码量显著高于均值（如 Table、Calendar、Picker 系）
2. **依赖隔离度**：自带三方依赖（qr_flutter、cached_network_image 等）或自身子模块多，全量接入时给不需要的用户带来额外依赖负担
3. **独立使用场景**：存在大量「只用这一个组件」的真实场景（如只想用 Picker/Table/QRCode 的 App）
4. **独立演进需求**：版本节奏/ Breaking change 与主库不同步（如 Picker 需要频繁迭代但主库求稳）
5. **体积影响**：含资源文件（字体、图片、图标）或显著增加包体积

### 不拆标准（命中即留在基础库）
- 被其他组件广泛依赖的基础能力（Space/Flex/Theme/ConfigProvider/Typography 等）
- 简单展示/布局组件（拆出去没有使用价值增益）
- 与其他组件强耦合、拆出需连带一堆依赖的

## 目标结构规划

### 基础库命名
- 已定名：**`antd_flutter_ui`**（基础组件库，内容以 UI 组件为主，语义直白；skill 命名对应 `antd-ui-dev`）

### 双端源码基线（重要约定）
- 现状：绝大多数组件基于 **antd v6（桌面端）** 源码实现，少数（标注 📱 的）基于 **antd-mobile v5（移动端）** 源码
- 本次拆分重构中做**双端兼容**评估：每个组件判断是否需要桌面版/移动版两套实现，**不是所有组件都需要**，判断标准：
  1. 交互形态双端差异大（如 Picker 桌面下拉 vs 移动滚轮、Table 桌面复杂操作 vs 移动简化）→ 倾向双实现或响应式自适应
  2. 双端视觉/交互基本一致（Button/Card/Tag 等）→ 单实现 + 响应式样式即可
  3. 仅单端有意义的组件 → 单实现
- 实现路径优先级：优先**单实现 + 响应式自适应**（经 AntResponsive 断点/设备类型切换形态），差异过大无法自适应的才做双实现；评估结论进拆分清单表
- 源码对齐基线：桌面组件以 antd v6 源码为准，移动组件以 antd-mobile v5 源码为准

### 共享引擎归属规则（用户确认）
- **跨包共享的引擎上移到 antd_flutter_ui**（`src/engines/` 目录）：
  - 滚轮选择引擎 + 列数据模型（antd_picker 全族消费）→ 上移后独立包间零互相依赖，依赖图扁平化：所有独立包只依赖 ui + theme（+ tokens/color 底层）
  - 虚拟键盘/格子输入模型（NumberKeyboard 族消费，未来自定义输入可复用）
- **单包独享的引擎留在该独立包内**，不上移（避免基础库用户承担无关体积）：Table 表格引擎、Tree 树引擎、瀑布流分配算法、Tour 挖孔遮罩、Splitter 拖拽分割、ImageViewer 缩放预览、PullToRefresh 状态机、SwipeAction 手势、Floating 拖拽吸附
- 判定标准：**被 ≥2 个包消费 → ui；仅 1 个包消费 → 留在包内**。Flutter AOT tree-shake 保证 ui 中未用引擎不进入产物
- 依赖方向约定：独立包 → antd_flutter_ui → antd_theme/tokens/color/icons；**禁止独立包之间互相依赖**

### 组件命名：antd 格式为主 + Flutter 别名层（用户确认）
- **规范命名保留 antd 格式**（与上游源码对齐）：`AntNavBar`/`AntTabBar`/`AntDrawer` 等，文档、示例、迁移指南均用 antd 名
- **新增别名层（继承转换）**：对与 Flutter 组件语义真实对应的组件，提供 Flutter 熟悉名作为**继承别名**（如 `class AntAppBar extends AntNavBar {}`、`class AntBottomNavigationBar extends AntTabBar {}`），Flutter 开发者可直接用熟悉名接入
- **别名准入标准**（防止滥用）：
  1. 语义真实对应（AppBar↔NavBar、Snackbar↔Toast 类可映射；Scaffold/Layout 无 antd 对应物则不造别名）
  2. 别名零新增逻辑——纯继承或 factory 构造，所有参数与行为完全一致
  3. 文档标注「别名，规范名为 XXX」；lint 提示优先用规范名（可加 dartdoc 建议，不强制）
- 命名映射表进入每库 skill（源码对比更新流程的一部分）

### 一键 antd 化扩展（原 P11 并入，重构时同步实现）
- `Text('123').antd` extension 语法：`.antd` 返回包装 Widget（`AntWrap`），build 内读主题（调用处无需 context，主题变化即时响应）
- 通用 `Widget.antd` 整体包裹（padding/圆角/水波纹）；`Text.antd`/`Icon.antd`/`Card.antd` 专用 extension 合并样式 token
- 合并策略：antd token 只补默认，用户显式 style 优先；限制：仅高频组件专用 extension，其余走通用包裹
- 与 Theme 桥接（P03）互补：桥接=全局默认，`.antd`=单点快捷
- 重构时同步实现：随各包迁移落地，每包迁移完成时该包组件的 `.antd` 支持 + alias 一并交付

### Flutter 标准库适配层（用户确认，补 theme 桥接细节盲区）
- **动机**：theme 桥接（P03）解决全局默认，但对 Flutter 独有组件族（**sliver 系列**：SliverAppBar/SliverList/SliverPersistentHeader 等）的细节默认值覆盖有限，antd 规范也无 sliver 概念
- **形态**：`antd_flutter_ui` 内设适配层目录（`src/adapt/`），产出 `AntSliverAppBar extends SliverAppBar`/`AntSliverList`/`AntSliverPersistentHeader` 等适配组件
- **实现原则（继承组件类本身，用户修正后定案）**：
  1. **`AntXxx extends <Flutter 组件类本身>`**（如 `class AntSliverAppBar extends SliverAppBar`）——类型兼容原生位置，可直接放进 `slivers:`/原组件位置，禁止退化为 StatefulWidget 包装
  2. antd 默认注入在**构造函数级**：可空参数走「null → antd token」解析辅助；非可空参数（如 bool 类）无法区分用户显式传值与默认值，保持 Flutter 原生默认，antd 需要不同预设时提供**具名构造**（如 `AntSliverAppBar.antd()`）承载 antd 预设
  3. 纯样式扩展仅用于无参数可注入的细节（内边距/分割线/状态样式）
  4. 用户显式传入的参数永远优先
- **细节校对机制（不用 golden 测试，用户确认：成本高且跨平台字体渲染易 flaky）**：
  1. 普通单元测试断言适配层组件默认参数值命中 antd token（便宜、确定性强）
  2. 视觉效果人工抽查：每包交付时在 example 页由用户肉眼验收，发现问题定向修复
- **范围**：首期 sliver 系 + theme 桥接后视觉仍不到位的组件（以 golden diff 结果为准逐步扩充）；适配层清单经用户确认
- 与别名层（AntAppBar extends AntNavBar）方向相反：别名层是「Flutter 名→antd 组件」，适配层是「antd 默认→Flutter 组件」，两者互补

## 归组判断说明（为什么这些放一起、那些分开）
- **归一族的唯一理由是共享同一套引擎/核心数据模型**：Picker 族共享滚轮引擎；Floating 族共享拖拽吸附引擎；NumberKeyboard 族共享虚拟键盘与格子输入模型；Tree/TreeSelect 共享树引擎；Upload/ImageUploader 共享文件选择与上传队列
- **共享引擎的归属再判定**：滚轮引擎与键盘/格子输入模型被多包消费 → 上移 `antd_flutter_ui/src/engines/`；其余引擎单包独享 → 留包内（见「共享引擎归属规则」）
- **PullToRefresh、SwipeAction 虽同为手势，但引擎互不复用、使用场景彼此独立** → 各自独立成包，不合并为「手势族」
- **Calendar 与 CalendarPicker 分属两包**：Calendar 是月视图引擎，CalendarPicker 是滚轮选择器，引擎不同（滚轮引擎已上移 ui，CalendarPicker 归 antd_picker 但不再依赖其他独立包）
- **ImageViewer 独立而 Image 留基础库**：预览缩放引擎重（InteractiveViewer+Overlay+手势），Image 本体是轻展示组件
- **AutoComplete/Mentions/Transfer/CheckList/Selector 留基础库**：它们本质是输入/选择组件，无重引擎依赖，拆出无增益
- 仍有争议的（Carousel/Masonry/Ellipsis 是否够格独立）以步骤 1 依赖审计数据 + 准入标准打分后由用户裁决

## API 文档体系（新增要求）
- 每个组件配套**详细 API 文档**，双轨产出：
  1. **dart doc 自动生成**：代码内 `///` 文档注释按 Effective Dart 规范补全（参数/返回/示例代码块），`dart doc` 生成 API 参考
  2. **人工编写的组件文档页**：组件简介、使用场景、参数表、事件表、代码示例（含亮暗/双端形态）、注意事项；Markdown 源文件（如各包 `docs/components/<name>.md`）
- 静态站点：以人工文档 + dart doc API 页构建静态页面（如用 md 手写页 + `dart doc` 输出整合，后续接 P02 的静态站点发布），供用户网页查看；结构预留与未来官网合并
- 文档随组件迁移同步搬迁，不放伞包

## 实现顺序（新增要求）
- **基础优先、无相互引用的组件先行**：拆分实施按依赖拓扑排序——
  1. 先底层包：tokens/color/theme/icons（已独立）→ antd_flutter_ui（含上移引擎）
  2. 独立组件包按「被引用数从少到多 + 引擎自足性」排序：完全无内部引用的组件包最先（如 antd_qrcode、antd_pull_to_refresh、antd_tour），被其他组件引用的（如 picker 引擎被 CalendarPicker 用，引擎已上移 ui 则解除）随后
  3. 步骤 1 依赖审计矩阵直接输出拓扑序，作为逐包实施的执行清单
- 每包迁移完成即补齐该包全部组件的双轨文档，再做下一包（文档不欠账）

## 步骤
1. **依赖审计**：扫描 111 个组件的 import 图，输出「组件 → 内部依赖 → 三方依赖」矩阵，量化每个组件的复杂度与耦合度，作为准入标准打分依据
2. **拆分清单裁决**：依据审计结果 + 准入标准给出最终拆分清单（含每个组件的去向和理由表）+ **双端兼容决策表**（单实现自适应 / 双实现 / 单端，附 antd v6 或 antd-mobile v5 源码依据），**提交用户确认后**才动代码
3. **基础库抽离**：建立 `antd_flutter_ui`（已定名），迁移基础组件（无接口变更，纯搬家 + export 路径调整），主包保留 re-export 保证兼容
4. **双端兼容落地**：按决策表逐组件实施（自适应形态经 AntResponsive 切换；双实现组件在单包内提供桌面/移动两个变体 + 自动选择）
5. **独立组件抽离**：按清单逐包拆出（每拆一包：建包 → 迁移代码+测试+example → Flutter 别名层 + `.antd` 扩展同步实现 → 主包 re-export → CI 更新 → 验证），一次一个包；共享引擎先行上移 ui（步骤 3 一并完成），保证独立包之间零互相依赖
6. **伞包整合**：`antd_flutter_plus` 改造为纯伞包（或保留少量 glue），全量接入 = 依赖伞包；单独接入 = 直接依赖 `antd_picker` 等
7. **CI/发布适配**：CI 矩阵覆盖全部子包；发布策略：基础库与伞包跟随主版本，独立组件库独立版本号（修订同步主库 token/theme 大版本约束）
8. **每库 Skill 编写**：经 skill-factory 为每个库生成配套 skill（组件清单/源码基线映射/双端决策表/源码对比更新流程），录入工作区技能体系
9. **文档适配**：README 接入方式说明（全量/按需）、组件表标注所属包与双端形态；**每组件双轨 API 文档**（dart doc 自动 + 人工 Markdown 文档页）随包迁移补齐，静态页面产出预留网页查看与 P02 站点整合

## 编码标准（全程适用）
- 遵循工作区规则（AGENTS.md / dev-conventions）：**DRY 原则**（重复字符串/数字/判断逻辑提取为常量或公共方法，常量命名体现业务语义）；**三方 SDK 中间件隔离**（SDK 方法经 wrapper/adapter 隔离，接口命名体现业务语义）
- 双实现组件的桌面/移动变体共享的样式/逻辑必须提取公共层，禁止复制粘贴两份
